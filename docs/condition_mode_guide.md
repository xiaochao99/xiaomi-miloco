# 触发规则条件模式使用指南

Miloco 支持三种条件检查模式，适用于不同的场景需求：

## 三种模式概览

| 模式 | 适用场景 | 摄像头 | HA设备 | Token消耗 | 响应速度 |
|------|---------|--------|--------|-----------|----------|
| **LLM模式** | 复杂语义理解 | 支持 | 支持 | 高 | 慢 |
| **直接模式** | 简单状态匹配 | 不支持 | 支持 | **零消耗** | **最快** |
| **混合模式** | 状态预筛选+视觉分析 | 支持 | 支持 | 中等 | 中等 |

---

## 1. LLM模式（默认）

### 适用场景
- 需要理解复杂自然语言条件
- 需要分析摄像头画面内容
- 条件涉及多设备联动判断

### 配置示例
```
条件类型: LLM模式
触发条件: 当主卧有人移动且灯是关闭的
生效设备: 主卧摄像头 + 主卧灯
```

### 特点
- ✅ 支持自然语言描述，灵活度高
- ✅ 可分析摄像头画面
- ✅ 支持复杂逻辑判断
- ❌ 消耗 LLM Token
- ❌ 响应速度较慢（需等待AI分析）

---

## 2. 直接模式（零Token）

### 适用场景
- 仅基于HA设备状态触发
- 简单的状态判断（开/关、数值比较）
- 追求极速响应和零成本

### 使用前提
- **不能选择摄像头**（仅HA设备）
- 条件需要使用结构化语法

### 支持的语法格式

#### 2.1 等式比较
```
state == on          # 状态为开启
state != off         # 状态不为关闭
temperature > 25     # 温度大于25
current <= 10        # 电流小于等于10
```

#### 2.2 列表包含
```
state in [on,open]           # 状态为on或open
state not in [off,closed]    # 状态不为off且不为closed
```

#### 2.3 正则匹配
```
state matches "on.*"         # 状态匹配正则表达式
state not matches "error.*"  # 状态不匹配错误模式
```

#### 2.4 检查特定属性
```
current > 0.5        # 检查current属性大于0.5
brightness == 255    # 检查brightness属性等于255
```

### 配置示例

#### 示例1：灯开启时触发
```
规则名称: 主卧灯开启通知
条件类型: 直接模式（零Token）
触发条件: state == on
生效设备: 主卧灯
执行动作: 发送米家通知
```

#### 示例2：温度超过阈值
```
规则名称: 温度告警
条件类型: 直接模式（零Token）
触发条件: temperature > 30
生效设备: 主卧温度计
执行动作: 发送米家通知
```

#### 示例3：多状态匹配
```
规则名称: 门窗开启检测
条件类型: 直接模式（零Token）
触发条件: state in [on,open,opened]
生效设备: 主卧门磁
执行动作: 发送米家通知
```

### 注意事项
1. **状态值格式**：Home Assistant的状态值通常是英文小写，如 `on`/`off`、`open`/`closed`
2. **设备多实体**：一个设备可能包含多个实体（如灯有switch和light实体），直接模式会检查所有实体，任一满足即触发
3. **不支持摄像头**：选择直接模式后不要添加摄像头设备

---

## 3. 混合模式

### 适用场景
- 既有摄像头又有HA设备
- 希望先用HA状态快速筛选，减少不必要的LLM调用
- 例如：只有灯开启时才分析摄像头画面

### 工作原理
1. **第一步**：使用直接模式快速检查HA设备状态
2. **第二步**：只有当HA条件满足时，才调用LLM分析摄像头

### 配置示例
```
规则名称: 开灯后人移动检测
条件类型: 混合模式
触发条件: state == on
生效设备: 主卧灯 + 主卧摄像头
执行动作: 发送米家通知
```

### 工作流程
```
灯关闭 ──→ 不满足条件 ──→ 不调用LLM ──→ 不触发
  │
  ↓
灯打开 ──→ 满足条件 ──→ 调用LLM分析摄像头 ──→ 根据AI判断触发
```

### 优势
- ✅ 减少不必要的 LLM Token 消耗
- ✅ HA状态检查速度快，快速排除无效触发
- ✅ 仍能利用AI进行复杂的视觉分析

---

## 模式选择决策树

```
是否需要摄像头？
├── 否 → 选择【直接模式】（零Token，最快）
│
└── 是 → 是否有HA设备？
    ├── 否 → 选择【LLM模式】
    │
    └── 是 → HA条件能否用简单语法描述？
        ├── 能 → 选择【混合模式】（省Token）
        └── 不能 → 选择【LLM模式】（复杂语义）
```

## 常见问题

### Q1: 直接模式设置了 `state == on` 但不触发？
A: 检查以下几点：
1. 确认设备在Home Assistant中的实际状态值（可能是 `on`、`open`、`true` 等）
2. 尝试使用 `state in [on,open,true]` 覆盖多种可能的值
3. 查看日志确认设备状态是否正确上报

### Q2: 为什么直接模式响应更快？
A: 直接模式在本地进行简单的状态比较，不需要调用远程LLM服务，因此：
- 无网络延迟
- 无AI推理时间
- 零Token成本

### Q3: 混合模式和LLM模式什么区别？
A: 两者都支持摄像头+HA设备，但：
- **LLM模式**：所有条件都交给AI判断（包括HA状态）
- **混合模式**：先用本地逻辑判断HA状态，满足后再调用AI分析摄像头

### Q4: 如何查看设备实际状态值？
A: 在Home Assistant开发者工具中：
1. 进入「开发者工具」→「状态」
2. 搜索设备实体
3. 查看 `state` 列的值

---

## 总结建议

| 场景 | 推荐模式 |
|------|---------|
| 只有HA设备，简单状态判断 | **直接模式** |
| 只有摄像头，需要视觉分析 | **LLM模式** |
| 有摄像头+HA，HA作为筛选条件 | **混合模式** |
| 有摄像头+HA，需要复杂联动判断 | **LLM模式** |
| 追求零成本、极速响应 | **直接模式** |
